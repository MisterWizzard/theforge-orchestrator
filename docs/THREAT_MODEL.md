# Initial Release Threat Model

> **A dated document.** Written on 26/09/2026 and updated in places since. Where it describes the system as it was then (for example a task "not yet registered", CI "red", or no web login), the later records in `docs/DECISIONS.md` and `docs/OPERATIONS.md` supersede it.

Reviewed 26/09/2026 (F091) against `main` @ `b8b0ed8` (merge of PR #18). Every control below was checked by reading the code and its test at the cited line; a control that exists only as a plan is not listed. Line numbers are as of this review's worktree (`wt/f091`), which changed `apps/coordinator/src/server.ts` only by adding `secretEquals` (six comparisons and one import block).

## Protected assets

1. **Repository integrity** — the target repository's default branch, the managed bare cache and worktrees under `FORGE_WORKSPACE_ROOT`, and, for Tier 0, the default branch of every repository on the merge allowlist.
2. **Credentials** — `FORGE_COORDINATOR_TOKEN`, `FORGE_WORKER_TOKEN`, `GITHUB_TOKEN`, `ANTHROPIC_API_KEY`/`OPENAI_API_KEY` or the isolated credential files (`FORGE_CLAUDE_CREDENTIALS_FILE`, `FORGE_CODEX_AUTH_FILE`), `FORGE_HA_TOKEN`, `FORGE_SMTP_PASSWORD`, the `gh` CLI's stored OAuth token, and worker session tokens.
3. **Worker control** — which host runs a job, in which container, with which mounts and egress.
4. **Approval decisions** — the digest-bound amber/red approvals and the standing Tier 0 allowlist.
5. **Durable run history** — the `events` hash chain, `usage_records`, `notifications`, `worker_jobs.result` (including raw provider tails), artifacts, retained failed workspaces.
6. **Budgets** — the daily cloud ceiling and per-task limits; a purchase check (`checkSpend`) that is implemented and tested but not yet called by the running system (see "Not covered").
7. **Availability of the control plane** — the coordinator, the worker, PostgreSQL, Redis, the local Ollama server, and the kill switch itself.
8. **Dan's attention** — the notification channels are the only way an unattended failure reaches a human; flooding or silencing them is an attack on asset 1 by proxy.

## Trust boundaries, as built

- **Coordinator API** (`apps/coordinator/src/server.ts`): every `/api/*` request needs `FORGE_COORDINATOR_TOKEN` except the worker endpoints, which need the worker token (registration) or a short-lived session token (`server.ts:92-98`, `:580-583`, `:345-348`). Since this review both tokens are compared in constant time (`packages/policy/src/index.ts` `secretEquals`; `server.ts:94`, `:465`, `:488`, `:514`, `:577`, `:620`). `/health` and `/metrics` are unauthenticated by design. Binds `127.0.0.1` by default (`apps/coordinator/src/env.ts:18`).
- **Web control centre** (`apps/web`): the browser never holds a token; the Next.js route `apps/web/app/forge-api/[...path]/route.ts:9-46` forwards to the coordinator with `FORGE_COORDINATOR_TOKEN`. Since ADR-027 an operator session stands in front of it: `apps/web/middleware.ts` requires a valid `forge_session` cookie (HMAC-SHA256 over `{issuedAt, expiresAt, nonce}`, key derived by HKDF from `FORGE_WEB_SESSION_SECRET` or the password, `apps/web/lib/auth/session.ts`) for every page and every `/forge-api/*` call except `/forge-api/health`, answering 401 JSON or a redirect to `/login`; with `FORGE_WEB_OPERATOR_PASSWORD` unset or under 16 characters everything but `/login`, `/logout` and `/forge-api/health` is a 503 (`apps/web/lib/auth/gate.ts`). The password is checked only by `POST /login/session` (`apps/web/app/login/session/route.ts`): same-origin form only, SHA-256 digests compared with `timingSafeEqual` (`password.ts`), five failures per source or fifty overall lock logins for a minute (`throttle.ts`). Mutations keep the same-origin header gate (`route.ts:16-29`) behind the session. The network boundary remains: `next start` binds `127.0.0.1` (`apps/web/package.json:7`) and so does `next dev` (`:6`).
- **Worker → provider CLI**: Claude and Codex run in a per-job Docker container from the digest-pinned image (`infra/docker/worker-sandbox/Dockerfile:1`, `USER node`), read-only root, dropped capabilities, workspace-only mount, bridge egress for providers and `--network none` for commands (except the dependency-install step, which runs alone on `bridge` before the sealed checks and can run dependency lifecycle scripts) (`apps/worker/src/index.test.ts:553`, `:485-540`). The credential enters over stdin into a tmpfs (`apps/worker/src/index.ts:1095-1120`). Since ADR-030 the container also declares itself the sandbox to the CLI inside it: every provider container carries `FORGE_EXTERNALLY_SANDBOXED=1`, set only where `docker run` is assembled (`sandboxProviderEnvironment()`), and the Codex adapter passes `--dangerously-bypass-approvals-and-sandbox` **only** on that exact marker — because Codex's own landlock/seccomp/user-namespace sandbox cannot initialise here and left the critic with no shell (BLK-016). What is removed is Codex's inner sandbox; this boundary is unchanged, and with the marker absent — anywhere on the host — Codex keeps its own.
- **Worker → local model server** (new, ADR-021): an `ollama` job runs **in the worker process**, not in the sandbox, over plain HTTP to `FORGE_OLLAMA_URL` (default `http://127.0.0.1:11434`, `apps/worker/src/env.ts:47`; `apps/worker/src/index.ts:1228-1236`). No credential is passed (`redactionValues: []`, `:1235`), no tools are exposed (`server.ts:246-253`, `tools: false`), and the reply is parsed and schema-validated before it becomes an event (`packages/provider-ollama/src/index.ts:164-230`, `adapter.test.ts:94`).
- **Coordinator → Home Assistant and SMTP** (new, F113): outbound HTTP with a bearer token to `FORGE_HA_URL` (`packages/notify/src/ha.ts:74-82`) and implicit-TLS SMTP with `AUTH PLAIN` (`smtp.ts:313-314`, `:269-272`).
- **Tier 0 → GitHub and the host** (new, PR #12/#14): `packages/tier0` runs on the host as the operator, through the operator's `gh` login, and executes a dependency pull request's `install` and `run <check>` scripts **on the host, in a temp directory, with no sandbox** (`packages/tier0/src/runner.ts:198-260`).
- **Filesystem**: `.env`, the halt file, the outbox, retained workspaces and the bare caches all live under the workspace root's parent, `C:\forge` on this host.

## Threats and controls

Each entry: the threat, the controls that exist in code, the evidence, and what the control does not cover.

### T1 — Prompt injection from objectives, repositories, tool output, model output or web content

- Controls: schema validation of every provider result at the adapter boundary (`packages/provider-claude/src/index.ts`, `packages/provider-codex/src/index.ts`, `packages/provider-ollama/src/index.ts:164-230`; `STRUCTURED_OUTPUT_INVALID` on mismatch); `assertUntrustedText` rejects common injection phrases at trust boundaries (`packages/policy/src/index.ts:188`); the reviewer verdict is advisory and approval is decided by the findings alone (`packages/workflows/src/index.ts:1189-1193`, `approvedByPolicy`); the repair prompt carries only blocking findings (`:1064`); the diff a reviewer sees is bounded at 200 KB (`:1000`, `:1020`); local-model output is treated exactly like cloud output — validated, redacted, never executed (`apps/worker/src/index.ts:971-1010`).
- Evidence: `packages/policy/src/policy.test.ts` "rejects common prompt-injection instructions"; `packages/workflows/src/pipeline-review.test.ts:160-208`; `packages/provider-ollama/src/adapter.test.ts:94`, `:268`; `docs/evidence-reviewer-prompt-2026-09-26.txt`.
- Not covered: a model that is _persuaded_ rather than _instructed_ — a plausible but wrong plan or review passes every schema. The deterministic check runner (ADR-016) and the human push approval are the backstop; there is no second-model cross-check unless the run configures a different critic provider, which no live run has yet done (F050/F051).

### T2 — Command or path escape from a worker job

- Controls: argument-array execution with `shell: false`; deny-by-default classification of commands, interpreters, package runners, network Git and secret locations (`packages/policy/src/index.ts:65-108`); canonical workspace containment and symlink rejection (`apps/worker/src/index.ts`, `assertContainedPath`); the mandatory Docker boundary for every production provider and command job (ADR-012); exact-action approvals bound to a digest (`packages/policy/src/index.ts:110-119`).
- Evidence: `apps/worker/src/index.test.ts:485`, `:503`, `:516`, `:532`, `:540`, `:553`; `packages/git-runtime/src/git.test.ts:44`, `:56`.
- Not covered: the `ollama` path has no container because it runs no commands and edits no files; the moment a local model is given tools or a builder role, this boundary must be revisited (ADR-022 forbids it today: `packages/guardrails/src/router.ts:248`, `LOCAL_FALLBACK_ROLES = ['planner', 'critic']`). Tier 0 is outside this boundary entirely (T11).

### T3 — Credential leakage into logs, events, artifacts, prompts, the database or a pull request

- Controls: known-secret plus pattern redaction on every provider event, command output and raw tail (`packages/policy/src/index.ts:139-175`: bearer tokens, JSON credential fields, AWS keys, PEM blocks, `token=`/`password=`/`api_key=` pairs, JWTs); the worker adds its own token and every string of the credential file to the known list (`apps/worker/src/index.ts:865`, `:1033-1061`); event payloads are redacted before publication (`server.ts` `createEvent` → `redactPayload`); the staged-diff gate refuses a commit containing a likely secret, now including `Bearer <token>` and JWT shapes (`packages/git-runtime/src/index.ts:281`, `packages/policy/src/index.ts:185`); Git receives `GITHUB_TOKEN` only through a temporary askpass launcher with credential helpers disabled and the directory removed afterwards (ADR-014; `packages/git-runtime/src/index.ts:75-130`); the notifier redacts `FORGE_HA_TOKEN` and `FORGE_SMTP_PASSWORD`, and their base64 forms, from every rendered message and error (`packages/notify/src/redact.ts:15-25`, `config.ts:97`); the halt file, outbox and Tier 0 outcome files hold no secrets by construction (`packages/tier0/src/report.ts:10-12` drops check output).
- Evidence: `packages/policy/src/policy.test.ts` (redaction fixtures); `apps/worker/src/index.test.ts:1020`, `:1115`; `packages/git-runtime/src/git.test.ts:86`, `:172`; `packages/notify/src/notifier.test.ts:108`, `smtp.test.ts:173`, `ha.test.ts:83`.
- Not covered: redaction is best effort (T9). `.env` itself is readable by every local account on this host (T10).

### T4 — Approval replay, mutation or bypass

- Controls: SHA-256 digest of the normalised executable, arguments, scope and worker; expiry; constant-time comparison (`packages/policy/src/index.ts:110-119`); the integration push is refused when the worktree HEAD no longer matches the approved commit, recorded as `integration.blocked{safety_constraint}` and escalated as critical (`apps/coordinator/src/escalation.ts:94-124`).
- Evidence: `packages/policy/src/policy.test.ts`; `apps/coordinator/src/server.test.ts:223`; run `9d6cf990` (BLK-004: an amber, digest-bound push scoped to one repository and commit).
- Not covered: Tier 0's merges carry no per-merge approval at all (T11).

### T5 — Duplicate or lost work after a crash, a worker loss or a halt

- Controls: PostgreSQL-fenced leases, heartbeats, idempotency keys, startup reconciliation (ADR-011); `createWorktree` recovers partial, junk and registered-but-deleted state (F130, `packages/git-runtime/src/index.ts:203-260`); worktrees are cleaned only after a completed push (`packages/workflows/src/index.ts:879`); the halt-aware wait does not count halted time (`server.ts:2049-2090`, `FORGE_WORKER_JOB_WAIT_MS`).
- Evidence: `tests/release-acceptance.test.ts:39`; `tests/worker-loss.integration.test.ts:26`; `tests/halt.integration.test.ts:69`, `:403`; `packages/git-runtime/src/git.test.ts:206-275`.
- Not covered: the restart test on a **real unattended batch** (F140, S5.3) has not been run; the live run `9d6cf990` was not restarted mid-flight.

### T6 — Tampering with or silently losing run history

- Controls (new, ADR-020): a `BEFORE INSERT` trigger chains every `events` row per run by `sequence` under a per-run advisory lock (`packages/db/src/migrations/006_audit_chain_and_notifications.sql:14-51`); `UPDATE`/`DELETE` on `events` and `audit_tombstones` raise unless the transaction opted in (`:56-72`, `:83-84`); retention removes whole terminal runs and writes a tombstone first (`packages/db/src/index.ts:952`, `:969`); `pnpm forge verify-audit` recomputes the chain in TypeScript and exits 1 on the first bad sequence (`packages/db/src/index.ts:531`; `packages/cli/src/commands/verify-audit.ts`).
- Evidence: `packages/db/src/audit.test.ts:74-263` (twenty concurrent appends, altered payload, deleted middle row, legacy rows, retention with tombstone); `packages/db/src/migration.test.ts:22`; `packages/cli/src/cli.test.ts:270-323`.
- Not covered: removing the _last_ row of a run, and anything the database superuser does with `set_config('forge.allow_event_delete','on')` — the chain proves integrity to someone who trusts the database host, not against it. Rows from before migration 006 are `legacy`, unverified.

### T7 — Runaway spend, runaway agents, or an unstoppable system

- Controls (new, F102/F112/F116): the kill switch is a plain file whose presence makes the lease route answer 204 (`packages/guardrails/src/limits.ts:65-186`; `server.ts:131`, `:694`); it is written by the API (`:468`), the CLI (`packages/cli/src/commands/halt.ts`) or by hand, survives a coordinator restart, and is honoured by the halt-aware wait; the daily cloud ceiling is checked before every cloud call with a per-role estimate, at run start and resume, and announced once per local day (`apps/coordinator/src/guards.ts:167-231`; `server.ts:1066`, `:1898`); the agent cap and free-memory floor gate every lease (`guards.ts:145-159`; `server.ts:701`); per-task tool-call, token and wall-clock limits abort a provider in the worker (`apps/worker/src/index.ts:971-1010`; `packages/guardrails/src/limits.ts:194-215`); the purchasing ban is **implemented and tested but has no production caller** (`packages/guardrails/src/spend.ts`), so it is not a live control - see the gap below; a policy-refused stage ends the run with a `safety_constraint` blocker instead of dispatching (ADR-022, `packages/workflows/src/index.ts:548-560`).
- Evidence: `tests/halt.integration.test.ts:69`, `:403` (real coordinator, real worker, SIGKILL and restart under a halt); `apps/coordinator/src/server.test.ts:412`, `:461`, `:485`, `:697`, `:925`; `apps/coordinator/src/guards.test.ts` (16), `guards.lease.test.ts`; `apps/worker/src/index.test.ts:928-997`; `packages/guardrails/src/guardrails.test.ts` (80, including the adversarial purchasing table).
- **Not covered, and this was previously overstated here: nothing in the running system refuses a purchase by name.** `checkSpend` is implemented, hardened and covered by an adversarial test table, but a repository-wide search finds **no production call site** - only its own test file. This document claimed until 04/10/2026 that "purchases are banned outright by action name, host and capability", which the call-site evidence never supported. An overstated control is worse than an acknowledged gap, because it stops anyone looking.
  - **What actually constrains financial activity today:** the daily cloud ceiling (bounds _cost_, not purchases); `--network none` on the command path (`apps/worker/src/index.ts:242-284`), so a check or test command reaches nothing at all (only the dependency-install step has network access, in a separate container that runs just the project’s declared install commands); and on the provider path, `bridge` networking limited in practice by the sandbox image's contents - digest-pinned `node:22-bookworm-slim` with only `git`, `pnpm`, `claude` and `codex`, read-only root, non-root user - rather than by any host rule. `BLOCKED_HOSTS` is **not** enforced at the network layer anywhere.
  - **What wiring it would take:** an adapter at the worker's provider-event boundary. `ProviderEventSchema`'s `permission_request.action` and `tool_request.name` (`packages/contracts/src/index.ts:353-370`) are the only model-authored action strings in the system, they are parsed and then **read by nothing**, and they have the same shape as `SpendAttempt.action`. Deliberately not done yet: a model naming a tool unluckily would refuse legitimate work, so it wants its own change with its own evidence.
- Not covered: **the kill switch file is only as protected as the directory it lives in** (T10): anyone who can write `C:\forge\...\FORGE_HALT` can halt the system, and anyone who can delete it can resume it, with no token and no audit event beyond the coordinator's log line. Codex reports `usd: 0`, so a Codex-heavy day is invisible to the ceiling (F111 gap; `guards.ts:55`). A local model costs nothing and is never refused, by design; its only limits are the per-task bounds and Ollama's own availability (T8).

### T8 — The local model server as an unauthenticated trust boundary on loopback

- The threat: `FORGE_OLLAMA_URL` is trusted configuration. The worker sends the full prompt for a planner or critic stage, unauthenticated, over plain HTTP to whatever answers on `127.0.0.1:11434`, and treats the reply as a model's output. Any local process — another user's session, a compromised dependency running under Tier 0 (T11), malware — that binds port 11434 first, or that Ollama proxies to, can read every prompt and answer with text of its choosing. It cannot obtain a credential this way (none is sent) and cannot run a tool (none is exposed), so the worst it can do is what a malicious model can do: steer a plan or a critique.
- Controls: no credential and no tool on the local path (`apps/worker/src/index.ts:1228-1236`; `server.ts:246-253`); output bounded at 10 MB and schema-validated (`packages/provider-ollama/src/index.ts:25`, `:164-230`); the builder and reviewer never run locally (`packages/guardrails/src/router.ts:248`); the deterministic check runner and the human push approval still stand between a bad plan and the repository; the worker only advertises models the server lists at startup (`apps/worker/src/index.ts:1261`), so a rogue server cannot make itself preferred — routing is decided by the ceiling, not by what is available.
- Evidence: `apps/worker/src/index.test.ts:778-850`; `packages/provider-ollama/src/adapter.test.ts` (15, one flag-gated real request); `apps/coordinator/src/server.test.ts:802`, `:891`, `:925`; ADR-021.
- Availability: the server stopped twice on 26/09/2026 under sustained load (11:47 silently, 12:57 mid-request, operator's report in this review's brief; the process observed running again from 13:03 local). The adapter maps a refused connection or a 5xx to a retryable `PROCESS_EXIT`, the pipeline retries once and then falls back to a cloud provider (`packages/workflows/src/index.ts:626-640`; `pipeline-routing.test.ts:263-314`) — which under the ceiling means the stage is refused and the run ends `partially_completed` (`:200`). A worker that started while the server was down never advertises `provider:ollama` until it restarts.
- Not covered: nothing authenticates the server, nothing pins its identity, and a `FORGE_OLLAMA_URL` pointing off-host would silently make this an egress path; the first real pipeline stage on a local model has **not** been observed (only the flag-gated ten-token smoke).

### T9 — Secrets at rest in retained workspaces and raw provider tails

- The threat: a failed job's checkout is kept as `<root>/.failed/<stamp>-<jobId>` with `RETAINED.json` (`apps/worker/src/index.ts:700-756`), exactly as the provider left it; the last 1,000,000 bytes of a sandboxed CLI's stdout and stderr are stored in `worker_jobs.result` (`:171`, `:936-947`; `packages/contracts/src/index.ts:26`). Both can contain whatever a model printed or wrote, including a credential it was shown in a repository file or an error message.
- Controls: the tails pass `redactSecrets` with the job's known values (`:865`) and the generic patterns before they are attached; they are readable only through `GET /api/runs/:id/jobs` behind the coordinator token (`server.ts:674`, hook `:92`) and never enter events, prompts, the UI or the CLI; `FORGE_RAW_OUTPUT` defaults to `failure`; retained workspaces are kept 5 deep for 72 hours (`apps/worker/src/env.ts:58-59`), swept at worker start and after every retention (`:379`, `:767`), and nothing serves them; the isolated credential never touches the workspace (tmpfs in the container).
- Evidence: `apps/worker/src/index.test.ts:228-416` (retention), `:1115-1176` (tails redacted, capped, mode-gated); `apps/coordinator/src/server.test.ts:586`.
- Not covered: redaction is pattern-based and misses a secret in an unfamiliar format, quoted in prose, or split across lines (`docs/OPERATIONS.md` "Redaction, and its limits"); a retained workspace is **not** redacted at all — it is a filesystem checkout, readable by anyone who can read `C:\forge` (T10); `worker_jobs.result` lives as long as the run.

### T10 — Local disk access: `.env`, the halt file, the outbox, caches and retained workspaces

- Observed on this host (icacls, 26/09/2026): `C:\forge` inherits the drive root's ACL — `BUILTIN\Users: (RX)` and `NT AUTHORITY\Authenticated Users: (M)`. Every local account can read `C:\forge\repos\TheForge\.env` (both tokens, `GITHUB_TOKEN`, any provider key), every retained workspace, every outbox file and every bare cache, and can create or delete the halt file.
- Controls in code: none can exist — the kill switch is deliberately a file so that it works with the coordinator down (policy B13, `docs/OPERATIONS.md` "Stopping the system"); the outbox is deliberately a file so that escalations survive without secrets. `.env` is gitignored (`.gitignore`). Provider credentials are read from isolated files rather than the operator's own `~/.claude` or `~/.codex` state (`apps/worker/src/index.ts:1033-1061`).
- Not covered: this is an operator finding, open. Smallest fix: restrict `C:\forge` to the operating user, SYSTEM and Administrators (`icacls C:\forge /inheritance:r /grant:r "<user>:(OI)(CI)F" "SYSTEM:(OI)(CI)F" "Administrators:(OI)(CI)F"`), then rotate both tokens. The machine is a single-user workstation, which is why this is a residual risk rather than a release blocker.

### T11 — Tier 0 merging code into a repository

- The threat: `pnpm tier0 <owner/repo> --execute` merges a dependency pull request into the default branch with `gh pr merge --squash --delete-branch` (`packages/tier0/src/runner.ts:406`) under the operator's `gh` login, whose token has the `repo` scope on every repository the operator can write to. Two distinct risks: (a) an unsafe upgrade lands; (b) the _verification_ itself is an attack surface, because the PR's dependencies are installed and its `test`/`lint` scripts run on the host with the operator's privileges — install scripts, test files and lint plugins of a compromised package all execute outside any sandbox (`runner.ts:198-260`, `mkdtemp` under the OS temp dir, `pnpm install --frozen-lockfile`, `pnpm run <check>`), with `.env`, `gh`'s token and everything under the operator's profile reachable.
- Controls: the merge allowlist is exactly two repositories (`MisterWizzard/shopfront` and `MisterWizzard/PulseApp`, ADR-035) and expansion is a recorded human decision (`packages/tier0/src/policy.ts:38-55`, policies B4/B5); only `dependabot[bot]` and `app/dependabot` are considered at all, checked first (`:90-95`); GitHub's own mergeability and behind-base signals, a non-empty check set and all-green checks are required (`:97-127`); the head SHA is fetched and checked out exactly so evidence and merge refer to the same code (`runner.ts:219-229`); mergeability is re-read immediately before the merge and a moved base is `deferred` with an `@dependabot rebase` comment rather than force-merged (`:287-330`, `:387`); `--execute` is the only mutating mode (`packages/tier0/src/cli.ts:25`); every outcome is written as JSON and ingested into the notification channels so an autonomous merge reaches Dan (policy B11; `packages/tier0/src/report.ts`; `packages/cli/src/commands/tier0-ingest.ts`); a failing run is retried once, then escalated, never handed to the paid pipeline (`policy.ts:158`).
- Evidence: `packages/tier0/src/policy.test.ts` (13), `runner.test.ts:60-286` (re-check, deferral, rebase comment gated on trusted authors, dry run never merges), `report.test.ts` (8), `packages/cli/src/cli.test.ts:515`; STATUS: 12 shopfront merges at $0, one escalation resolved by rebase, one human PR skipped.
- Classification: SECURITY.md lists "merge to protected branches" as Red. Tier 0 performs it under a **standing** approval (the allowlist) rather than a per-action one. This review records that as an Amber action under policy B4/B5 in `docs/SECURITY.md` and in ADR-019, confined to two low-stakes repositories; it is not a per-merge Red approval and must not be described as one.
- Not covered: the host-execution risk in (b) has no mitigation today. Policy C6 allows major bumps to merge on green checks (`policy.ts:129-132`), a recorded risk. The `gh` token is far broader than the fine-grained `GITHUB_TOKEN` the pipeline uses (BLK-004 confirmed that one returns 404 for other repositories; the CLI login does not).

### T12 — The notifier's outbound channels and their secrets

- The threat: the coordinator now makes outbound calls with two long-lived secrets. `FORGE_HA_TOKEN` is a Home Assistant long-lived access token sent as a bearer over `FORGE_HA_URL`, which on Dan's network is **plain HTTP** (`http://192.168.1.10/ha`, `.env.example:45`; `packages/notify/src/ha.ts:74-82`): anyone on the LAN path can read the token and use it against the whole Home Assistant API, not only `notify`. `FORGE_SMTP_PASSWORD` is a Gmail app password sent with `AUTH PLAIN` inside implicit TLS (`smtp.ts:313-314`, `servername: host`, so certificate and hostname are verified by Node's defaults). A notification body can carry a run's objective, a finding's claim and a blocker's text — model-influenced content — to a phone and a mailbox.
- Controls: both secrets are optional and absent today, so nothing but the file outbox delivers (`config.ts:60-99`; STATUS); each channel is independent, retried three times with backoff, and a failure never propagates into the event path (`notifier.ts`; `apps/coordinator/src/escalation.ts:526`, `server.ts:315`); dedupe (6 h) and coalescing (5 min) bound the message rate so a flapping run cannot flood the phone (`notifier.ts:5-14`); recipient addresses are validated against SMTP injection (`smtp.ts:135-139`); the HA body is capped (`ha.ts:28`); the secrets and their base64 forms are redacted from every message and error (`redact.ts`); the notifications table records each delivery per channel (`006_audit_chain_and_notifications.sql:86-103`).
- Evidence: `packages/notify/src/*.test.ts` (43 tests against in-process fakes); `apps/coordinator/src/escalation.test.ts` (17); `packages/cli/src/cli.test.ts:411-475`; `docs/evidence-notify-2026-09-26.txt`. **No real Home Assistant or Gmail delivery has ever occurred.**
- Not covered: the HA token travels in clear on the LAN; the Home Assistant token cannot be scoped to `notify` only; a stolen app password sends mail as Dan. Neither channel has been proven live; the first real escalation may fail for a reason no fake could show.

### T13 — Scheduled tasks running as the interactive user

- Observed on this host (Get-ScheduledTask `\TheForge\`, 26/09/2026): `TheForge Digest Morning` (05:00) and `TheForge Digest Evening` (17:30) are registered, `Ready`, `LogonType Interactive`, `RunLevel Limited`, user `operator`, never run yet (`0x41303`). The coordinator and worker tasks are **not** registered.
- The threat: a scheduled task runs `pwsh -ExecutionPolicy Bypass -File <checkout>\scripts\run-digest.ps1` from the checkout, so anyone who can write the checkout or `.env` runs code as Dan at 05:00 and 17:30 (`scripts/register-digests.ps1:75-89`); the future runtime tasks would do the same at every logon, restarted up to 999 times (`scripts/runtime/register-runtime.ps1:124-135`), turning a persistent foothold into a supervised one. Because the principal is the interactive user, the tasks carry Dan's full profile: `gh` login, Docker, cloud sync.
- Controls: `RunLevel Limited` (never elevated); Interactive logon type, so nothing runs without a session and no password is stored (`register-digests.ps1:82-83`; `register-runtime.ps1:130`); the digest reads the database and writes the outbox only; registration is a manual operator step, refused on a failed `pnpm forge runtime doctor` (`docs/OPERATIONS.md` "Running TheForge as a service"); the 15-minute execution limit on digests (`register-digests.ps1:81`).
- Not covered: T10 makes "who can write the checkout" every local account. There is no code-signing or hash check of the runner scripts.

### T14 — Provider compromise, unsupported claims, or a provider that is down

- Controls: provider-neutral boundary (ADR-001, ADR-021 added a third provider without touching orchestration); independent reviewer role; deterministic verification in the worker rather than the model (ADR-016: builder gets `acceptEdits`, every other role `dontAsk`, `packages/provider-claude/src/index.ts:80`; `adapter.test.ts:211`, `:217`); one retry then a fallback to the other cloud provider, never a retry of a builder that left edits behind (`packages/workflows/src/index.ts:626-640`; `pipeline-routing.test.ts:263-404`).
- Evidence: run `9d6cf990` (live, Claude every role); `packages/workflows/src/pipeline-routing.test.ts` (12).
- Not covered: no live run has used two providers, so "independent reviewer" is a configuration option, not an observed property (F050/F051).

### T15 — Worker takeover or an exposed control plane

- Controls: worker registration needs the shared worker token; every later worker call needs a short-lived session token bound to the worker id (`server.ts:580-583`, `:345-348`, `:677-681`); `HOST` defaults to loopback; CORS restricted to `FORGE_WEB_ORIGIN`; no unauthenticated command endpoint; workers are expected on Tailscale (ADR-007). The web control centre requires the operator session before the BFF forwards anything but `/forge-api/health` (`apps/web/middleware.ts`, `lib/auth/gate.ts`, ADR-027); the login form is password-only, same-origin only, compared in constant time and throttled per source and overall (`apps/web/app/login/session/route.ts`, `lib/auth/password.ts`, `lib/auth/throttle.ts`); the app fails closed to 503 when the password is not configured.
- Evidence: `apps/coordinator/src/server.test.ts:97`, `:125`, `:223`; `tests/worker-portability.integration.test.ts:57`; `apps/web/lib/auth/session.test.ts`, `gate.test.ts`, `password.test.ts`, `throttle.test.ts`, `config.test.ts`, `request.test.ts`; `tests/e2e/operator-login.spec.ts` (redirect, 401, wrong and right password, cookie attributes, logout, lockout, cross-site form refused).
- Not covered: the web session is a stateless bearer cookie, so a copied `forge_session` is valid until it lapses (12 h) or the signing material changes, and "Log out" revokes nothing server-side; the login throttle lives in the web process and is forgotten on restart; the source label comes from `x-forwarded-for` when present, which only the overall cap defends; `/health` and `/metrics` leak operational detail to anyone who can reach the port.

### T16 — Supply-chain compromise of TheForge itself

- Controls: frozen lockfile in CI and in every gate; `pnpm audit --prod` blocking in CI and clean on 26/09/2026; the full audit non-blocking in CI, dispositioned in `docs/evidence-dependency-audit-2026-09-26.txt` (three dev-only advisories accepted, three patched by override); GitHub Actions pinned to commit SHAs (`.github/workflows/ci.yml`); the sandbox image pinned by digest with pinned CLI versions (`Dockerfile:1-5`); `allowBuilds` limits which packages may run install scripts (`pnpm-workspace.yaml`).
- Not covered: Tier 0 deliberately installs and runs _other repositories'_ dependencies on this host (T11) — the strongest supply-chain control here is undone there.

## Residual risks, stated plainly

1. **Every local account on this workstation can read the secrets and flip the kill switch** (T10). Not fixed in code; needs an ACL change and a token rotation by the operator.
2. **Tier 0 executes untrusted dependency code on the host as the operator with a broad `gh` token** (T11). Contained only by the two-repository allowlist and Dependabot-only authorship.
3. **The Home Assistant token will travel in clear on the LAN** once it exists (T12), and neither notification channel has delivered a real message.
4. **The web control centre's session is stateless** (T15). Since ADR-027 a login is required and the app fails closed without a password, but a copied `forge_session` cookie stays valid until it lapses or `FORGE_WEB_SESSION_SECRET` (or the password) changes, and the failure throttle lives in the web process. Serve it over HTTPS on the tailnet only; `pnpm dev` bound all interfaces until the previous review.
5. **The local model path is unauthenticated on loopback** (T8) and has not carried a real pipeline stage; the server itself fell over twice today under load.
6. **Redaction is best effort** (T3, T9); retained workspaces are not redacted at all.
7. **The audit chain trusts the database host** (T6); legacy rows are unverified.
8. **Codex spend is invisible to the ceiling** (T7, F111).
9. **CI on `main` has been red since `8d51928` (PR #14)**: two test defects, both fixed in this review and reproduced locally, but the fix is unverified in CI until it merges (`docs/RELEASE_REVIEW.md`).
10. **Nothing has run unattended.** The coordinator and worker are not registered as tasks, the restart test on a real batch has not been run, and the digests have not yet fired once.
11. Docker, the pinned provider CLIs, Ollama, PostgreSQL and Task Scheduler remain trusted computing-base components; hosted multi-tenant isolation is outside this release; macOS is deferred (ADR-015).
