== What is true now ==

buildReviewPrompt      defines the four severities, asks for diff-supported findings citing file and hunk, states that
                       formatting/import order/whitespace are never above low, and states the approval rule. The closing
                       verdict sentence is byte-identical to the old prompt, so parseReview's contract is unchanged.
REVIEW_DIFF_LIMIT_BYTES = 200 * 1024. A larger diff is cut at the last line break inside the limit; the DIFF header then
                       says how many bytes were shown and how many were not, and `git diff --stat=200 --no-ext-diff` is
                       appended so every changed file is named. The stat is fetched once per review round.
parseReview            approved = no high/critical finding. The reviewer's own flag is advisory: approved:false (or any
                       non-true value) with nothing blocking gives approved:true plus approvedByPolicy:true, which the
                       review.completed payload carries (`...verdict`). approved:true beside a high finding is still not
                       approved. No parseable verdict still yields one synthetic high finding, never approved.
renderRepairPrompt     numbered list of the high/critical findings only, each as "[severity] claim / Action: action", with
                       the instruction to fix those and nothing else. Low/medium findings are not sent to the builder;
                       they stay on review.completed, which apps/coordinator/src/server.ts:1463 already records as
                       Findings.

== Final reviewer brief (rendered by buildReviewPrompt; placeholders in angle brackets) ==

Review the actual diff against the objective and the revised plan. Be evidence-based: report only findings the diff supports, and cite the file and the hunk in every claim.
Severity scale:
- critical: the change is wrong, unsafe, or violates the objective.
- high: must be fixed before merge - a real defect, a missing test for changed behaviour, or a security or data-loss risk.
- medium: should be fixed; does not block the merge.
- low: style, naming, formatting; never blocks.
Formatting, import ordering, and whitespace are never above low.
Set "approved" to true when there is no high or critical finding.
End with a JSON object {"approved":boolean,"findings":[{"severity":"low|medium|high|critical","claim":"...","action":"..."}]}.
OBJECTIVE:
<objective>
PLAN:
<revised plan>
DIFF:
